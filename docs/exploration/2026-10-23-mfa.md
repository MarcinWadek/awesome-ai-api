# MFA lifecycle exploration

**Date:** 23 October 2026. **Target:** configured API host `https://awesome.byst.re`.
The parent agent performed this work directly; no subagents were used for MFA.
Sources: saved [OpenAPI](../api-docs.json), read-only backend `UserMfaController`,
`MfaService`, `TotpService`, `MfaProperties` and existing backend test source.
The deployment revision/profile was not identified; backend tests were not run.

## Method and observations

A bounded runner at gitignored `exploration-results/mfa-probe.mjs` used one owned
local-password target plus an independent ordinary observer. Both had unique
`example.invalid` emails. Its sandbox execution failed before signup; the
network-enabled run completed. No shared account or administrator was mutated.
Only status codes, nonsensitive provisioning parameters and counts were output.
Secrets, QR contents, passwords, tokens and recovery codes stayed in memory.

| Request / assertion | Observed |
| --- | --- |
| Initial status | 200, disabled, zero recovery codes |
| Anonymous status/setup/confirm/replacement/disable | 401 for each |
| Setup | 200; consistent Base32 secret/OTPAuth URI, SHA-1, six digits, 30-second period, PNG data URI |
| Status after setup | Still disabled with zero recovery codes |
| Invalid six-digit confirmation | 401; status remained disabled |
| Confirmation with current TOTP | 200; enabled status, eight recovery codes |
| Refresh token issued before confirmation | Rejected with 401 |
| Password login with MFA enabled | 200 challenge; access and refresh tokens null |
| Confirmation code reused for sign-in | 401 |
| Fresh TOTP on the challenge | 200; issued access token read the expected `/users/me` profile |
| Completed challenge reused with an unused recovery code | 401 |
| Recovery-code login | 200; reuse on a fresh challenge returned 401 |
| Recovery replacement with wrong password | 422 |
| Replacement with correct password and fresh TOTP | 200; an old code was rejected with 401 on a fresh challenge |
| Disable with correct password and invalid factor | 401 |
| Disable with correct password and unused recovery code | 200, empty body; status disabled with zero codes |
| Previously issued MFA-session refresh token after disable | Rejected with 401 |
| Password-only login after disable | 200 with session tokens and no MFA challenge |
| Cleanup | Both owner deletes returned 204; observer lookup confirmed target absence with 404 |

The setup response Date header was approximately 182ms behind the local clock
at receipt. This was a diagnostic observation, not an authoritative clock-offset
measurement or proof of the server's entire acceptance window. The runner used
current time steps and bounded waits, without retrying rejected credentials or
generating future-step codes.

## Timing and implementation implications

Confirmation consumes the TOTP step, so another successful TOTP action requires
a fresh step. The helper reserves a submitted step even if its response is lost,
avoids the final three seconds of a period, and waits at most one period plus a
small margin. Six-digit SHA-1 provisioning is supported; incompatible provisioning
fails explicitly. An invalid code is selected outside a seven-step local window,
wider than the inspected source's adjacent-step configuration. Wider deployed
acceptance settings would require a fresh compatibility review.

The generator was checked against all six SHA-1 examples in
[RFC 6238 Appendix B](https://www.rfc-editor.org/rfc/rfc6238.html#appendix-B),
including their eight-digit results and derived six-digit suffixes. This is a
test-client helper, not a new authentication implementation for the application.

Existing access JWTs remained usable for status and owner cleanup after
confirmation and disable. Refresh revocation does not imply access-JWT revocation.
MFA-aware teardown retains the authenticator so it can complete a new login when
the stored access token is rejected; deleting the account does not require first
disabling MFA. The independent observer remains alive through target teardown.

## Limits

The 16 selected automated cases and their verification are recorded in the
[implementation record](../implementation/mfa-lifecycle-tests.md). No application
defect was identified by the initial lifecycle probe. Full setup/challenge expiry,
exact skew boundaries, rate-limit saturation, concurrent consumption, SSO-managed
MFA, password-reset interaction and exhaustive 400/409/410/422 combinations remain
outside this batch. Successful disable uses a recovery code; the TOTP alternative
is not separately automated. Recovery replacement checks a representative old
code and a new code, not every member of both sets.

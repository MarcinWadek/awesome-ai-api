## SSO: enabled exchange is unavailable on current targets

| Target / condition | Observed |
| --- | --- |
| awesome: missing ID token, no Authorization | 400 with `idToken` validation error |
| awesome: nonblank synthetic ID token, no Authorization | 404 with `SSO login is disabled` |
| aitesters: same two conditions | The same 400 and explicit disabled-SSO 404 |
| Local Keycloak discovery at localhost:8082, realm awesome-testing | Unreachable on the network-enabled check |

No SSO/IdP settings were found in the test repository environment, and Docker CLI
was not available on the current PATH. Local reference configuration includes a
Keycloak realm, but it is not a running or trusted issuer for the remote hosts.
No shared IdP credentials, seeded identity or arbitrary signing key was used.
The user was asked whether an enabled test API/IdP is available; this delivery
proceeds with the independently verified current deployment behavior.

The backend checks its SSO-enabled flag before decoding tokens. Its 404 therefore
does **not** establish signature, issuer, audience or expiry rejection. Missing
input is validated before that flag and returns 400. Backend controller tests use
a mocked login service; reading them does not prove a real exchange works.

The two permanent SSO tests assert exact 400/404 behavior, not a flexible set of
401/404 responses. A deployment enabling SSO will require an intentional scope
change. Successful exchange, provisioning/linking, client privileges, valid-token
reuse, conflicts and meaningful invalid-token 401 checks need an enabled API plus
a trusted IdP capable of issuing tokens for disposable identities. No exchange
success or new SSO account is claimed or created here.

## Email: acceptance, event recording and isolation

A bounded runner created two ordinary disposable accounts with unique
example.invalid recipients. The observer/peer started with an empty event list;
the sender did too. Only one valid message was sent, to the sender's own address.

| Condition | Observed |
| --- | --- |
| Authenticated request with only recipient malformed | 400, `{ "to": "Invalid email format" }`; sender events still empty |
| Anonymous otherwise-valid request | 401; sender events still empty |
| Owned valid request | Empty 200 |
| Sender event read immediately afterward | One GENERIC event, QUEUED, expected masked recipient |
| Peer event read afterward | Still empty |
| Cleanup | Both owner deletes returned 204; an observer lookup confirmed the sender absent with 404 |

The event fields were `type`, `status`, `recipientMasked`, `createdAt`, `updatedAt`
and `failureReason`. No full recipient, subject or message appeared in this
metadata. The permanent test verifies those fields, valid timestamps, a nullable
failure detail and a known lifecycle state. It allows QUEUED, SENT_TO_SMTP_SINK or
FAILED as recorded metadata: none alone proves delivery, and FAILED would indicate
an unsuccessful later handoff rather than successful delivery. The five-second
poll is for event creation only; it does not wait through the delayed send.

No Mailhog/outbox body, SMTP sink, message delivery or message-content rendering
was inspected. Queued background work may outlive account deletion. Tests use
the existing registered-user fixture's 204 owner cleanup; they do not query
every deleted record or clear a shared outbox.

How the framework works

WORKING WITH THE FRAMEWORK

Contributor guide

Find the right fixture, add a focused test and verify the result.

npm ci  →  configure .env  →  npm test
RUN

Setup and commands

Use Node.js 24+ and npm 10+. No browser installation or local backend is required.

npm ci
cp .env.example .env

In PowerShell use Copy-Item .env.example .env; use npm.cmd/npx.cmd if script execution policy blocks npm. Fill .env with authorized test-account credentials:

Project Default URL Credential variables
api https://awesome.byst.re API_LOGIN_USERNAME, API_LOGIN_PASSWORD
admin https://aitesters.byst.re ADMIN_API_LOGIN_USERNAME, ADMIN_API_LOGIN_PASSWORD

API_BASE_URL / ADMIN_API_BASE_URL select URLs; admin authentication enforces the staging origin. The admin project also includes ordinary staging shoppers. Absent URL values use defaults; blank values fail. Shell/CI variables override .env; credentials are loaded only when configured-account sign-in is needed. Discovery needs no credentials. Never commit .env, tokens or generated reports.

Commands

Task Command
Discover without API requests npx playwright test --list
Both remote projects npm test
API / staging only npm run test:api / npm run test:admin
One spec npm run test:api -- tests/api/users/me.get.spec.ts

Offline fixture checks npm run test:fixtures

For behavioral changes, run affected tests first, then:

npm test -- --project=api --project=admin --workers=4 --retries=0

Live runs create data. Fixtures clean up most owned resources; signup tests retain accounts, and interruption can prevent teardown. Retries and traces are disabled. Keep the redaction reporter first, including reporter overrides; do not log secrets.

After setup, read the profile spec or checkout workflow. Coverage lists checks/gaps; Bug reports records unexpected behavior.

01

Where changes belong

Location Responsibility
tests/api, tests/admin API-host and staging-host scenarios; staging includes ordinary shoppers
clients, types HTTP methods and request/response types
fixtures Inject clients and own account/resource lifecycles
generators Unique registration data; override fields for validation cases
support Assertions, configuration, SSE/TOTP helpers and error redaction

Types need runtime assertions. Check status, headers, fields and persistence; reuse existing helpers.

02

Choose the fixture

Import test and expect from the narrowest suitable entry point:

Fixture Use when
clients Anonymous requests or explicit configured-account login
auth A fresh ordinary account; optional authenticatedPeer for isolation
admin Staging administrator access; origin is guarded to https://aitesters.byst.re
account lifecycle The scenario deletes its account; an observer verifies absence
MFA Enrollment, second-factor login or recovery
commerce Owned shoppers/products/orders and stock restoration

Clients and resources are lazy and test-scoped. Inject clients in test callbacks; keep scenario-specific preparation visible in the test or setup hook.

03

Add or change a test

  1. Check the saved OpenAPI contract, existing specs and target behavior. Backend source can explain behavior but does not prove deployment state.
  2. Select success, authentication and meaningful negative cases. Add boundaries and ownership checks for distinct risks.
  3. Use one METHOD /path describe, a method-bearing filename and flat status: behavior names ordered by response code. Separate preparation, request and assertions with // Given, // When, // Then; omit empty sections. Reserve test.step for useful workflow/lifecycle groups.
  4. Verify persistence/state preservation. Report defects without weakening assertions, skipping or adding retries.
  5. Run affected tests first, then the full api/admin suite for behavioral changes. Run fixture checks for lifecycle changes, typecheck and whitespace checks. Update coverage with dated outcomes/gaps. Documentation edits need link/content checks. Record blocked execution honestly.
04

Own data through teardown

  • Keep tokens, users and IDs within one environment. Use generated identities and owned products; never modify, log out or delete the shared administrator.
  • Ordinary auth owns account deletion. Use specialized fixtures if changing credentials, enabling MFA or deleting the account inside the test.
  • Commerce clears carts, cancels orders and restores stock before account deletion; products follow account/order removal. Preserve dependent data and report failures if restoration fails. Do not bypass this order.
  • Recover resources after lost responses using unique names; verify cleanup after setup/assertion failures. Signup retention and interruption remain limits. MFA renewal requires fresh TOTP windows, not fixed sleeps.
  • Traces stay off. Keep the redaction reporter first, including CLI overrides; never log/attach credentials or enable request debug output.
05

AI checks

Ollama specs exercise deterministic mock scenarios. They verify SSE framing, reconstructed text, tool schemas/results and the final assistant phase. Consume the whole stream: intermediate done events do not end a tool workflow. See SSE parsing and tool assertions.

Exact mock prose checks transport expectations, not real-model quality or grounding. Buffered responses do not measure token latency. Mutable price/stock comparisons require isolated data; the known mock/prose mismatch is in Bug reports.

06

How the framework evolved

Development moved from contract exploration and authentication to reusable fixtures, AI integration, staging CRUD, commerce and MFA. Review then reduced repetitive cases and unified clients, cleanup and test style.

Parallel work included two GPT-6 Luna subagents on 23 October 2026: account-lifecycle implementation and password/email exploration. Parent review corrected and verified their output. Earlier workstreams were plans; MFA and email/SSO were direct deliveries. Agree interfaces/file ownership before delegating, then integrate and verify. Concurrent workers need isolated data. Defect regressions Prompt parsing/types, incompatible QR Accept and deleted-account JWT errors; see BUG-002–004 in Bug reports
Isolation Signup retains accounts; interrupted processes or API outages can prevent cleanup

BUG-001

final mock answer disagrees with tool data

Mock limitation

Observed: 11 October 2026. Status: mock limitation; fix unconfirmed.

Reproduce: sign in, fetch /api/v1/ollama/chat/tools/definitions, then POST /api/v1/ollama/chat/tools with those tools, model qwen3.5:2b, stream: true and the user message What iphones do we have available? Tell me the details about them. Consume the complete SSE response and compare final prose with get_product_snapshot.

Expected: product facts match tool results. Actual: snapshot price/stock was 999.99/47; final prose stated $999/5. Mock final prose was a fixed string. Current test checks tool payloads and mock prose separately; passing it does not establish answer grounding or a real-model defect.

BUG-002

a deleted account's JWT can produce 500

Fix unconfirmed

Observed: 23 October 2026. Status: fix unconfirmed.

Reproduce: register/sign in, retain the JWT, delete the account through DELETE /api/v1/users/{username}/right-to-be-forgotten, then repeat DELETE or GET /api/v1/users/{username} with that JWT.

Expected: a documented authentication/missing-resource error; precedence needs confirmation. Actual: 500. The lifecycle test verifies absence through an independent observer; it does not accept 500 as cleanup success or assert immediate access-JWT revocation.

BUG-003

prompt request parsing and type validation

Fix unconfirmed

Observed: 6 October 2026. Status: fixes unconfirmed; intended-behavior regressions are not automated.

Reproduce: with a valid JWT, PUT /api/v1/users/chat-system-prompt using malformed JSON, no body or {"chatSystemPrompt":{}}; repeat with {"chatSystemPrompt":123}. The tool-prompt endpoint behaves similarly with toolSystemPrompt.

Expected: 400 validation errors, preserving the previous value. Actual: malformed/object requests return 401 although subsequent GET works; numeric input returns 200 and persists "123". See the chat-prompt spec for current scope.

BUG-004

QR Accept negotiation returns 401

Fix unconfirmed

Observed: 20 October 2026. Status: fix unconfirmed; incompatible-Accept regression is not automated.

Reproduce: with a valid JWT, POST /api/v1/qr/create with JSON {"text":"https://example.invalid/qr-core"} and Accept: application/json. Repeat with Accept: image/png, application/json.

Expected: a media-negotiation rejection for JSON-only Accept and 200 PNG for compatible Accept. Actual: 401 for JSON-only, 200 for compatible headers. Current QR tests use compatible Accept.

BUG-005

existing traffic detail returned 500

Not reproduced on recheck

Observed: 20 October 2026. Status: did not reproduce on 23 October; root cause/fix unconfirmed.

Reproduce: generate a unique api_<UUID> session header, GET /api/v1/traffic/info, find that request in the session-scoped /api/v1/traffic/logs?page=0&size=10, then GET /api/v1/traffic/logs/{correlationId} with the same X-Client-Session-Id.

Expected: 200 with the captured entry. Actual: 500 for found entries; fresh unknown IDs returned empty 404. The regression test retains the 200 assertion and passed on the last recorded recheck. This covers legacy public traffic mode, not protected mode.
